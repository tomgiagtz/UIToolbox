Third-party components · Lesson 1

The Color object, not a color string

Before you swap in React Aria's field, you have to see the one thing that makes it different from yours: what it holds in state.

Your goal for this mission is to reach for a library component — React Aria's ColorPicker — and wire it into UIToolbox deliberately, not by pasting the docs and hoping. The way in is always the same five questions. Learn them once; they work on any library.

The reading method When you meet an unfamiliar component, ask, in order: (1) what state does it own? (2) what shape is that state? (3) how do value/onChange flow? (4) how do its subcomponents share that state? (5) how is it styled? This lesson is entirely questions 1 and 2. The rest are later lessons.

What your field holds today

Your ColorField in glyph-creator/controls-ui.tsx is a textbook controlled component. Its state is a string: 

// controls-ui.tsx (yours)
value: string;                       // e.g. "#ff8800"
onChange: (value: string) => void;  // a string comes back out

That string is all your app ever knows about the color. It flows straight into project state — project.textColor is a string, and style-controls.tsx dispatches { color } as a string. Nothing wrong with that. Hold onto it — it matters at the end.

What React Aria holds instead

React Aria's ColorField (and the ColorPicker that coordinates several of them) does not hold a string. It holds an immutable Color object. Its onChange hands you a Color, never a string (docs): 

import { parseColor } from "react-aria-components";

// state is a Color object, made from a string via parseColor:
const [color, setColor] = useState(parseColor("#f80"));

<ColorField value={color} onChange={setColor}>  {/* onChange gives a Color */}
  <Input />
</ColorField>
The whole lesson in one line Your field's state is a string; React Aria's is a Color object. Every other difference — channels, sliders, color-space dropdowns — falls out of that one fact.

Why an object beats a string

A string like "#ff8800" is opaque. To ask “what's the red channel?” or “what's this in HSL?”, something has to parse it first. A Color object is that parsed form — so it can answer directly:

→ color.getChannelValue("red") Read one channel as a number — 255. A string can't do this without parsing.
→ color.toFormat("hsl") Re-express the same color in another space. This is how one picker drives RGB and HSL fields.
→ color.toString("hex") Serialise back to a string — "#FF8800". Your exit ramp back to app state.
✓ parseColor("not-a-color") Validates on the way in — an invalid string throws, rather than silently poisoning state.

So the object isn't ceremony. It's the reason a single picker can offer a hex box, three RGB number fields, a hue slider, and a 2-D area — all editing one value. (That composition is Lesson 2.)

The catch — and the seam that solves it

Here's the tension for your migration. React Aria wants Color objects. But your project state is string-based and should stay string-based — you don't want to rewrite the whole glyph-creator reducer to adopt one field. Both can be true. You put an adapter at the boundary: 

// The seam: string app  ↔  Color-object component
<ColorField
  value={parseColor(project.textColor)}                 {/* string → Color, going in  */}
  onChange={(c) => dispatch({
    type: "set-text-color",
    color: c.toString("hex"),                            {/* Color → string, coming out */}
  })}
>
  <Input />
</ColorField>
Watch onChange can hand you Color | null (the field can be cleared). And parseColor throws on a bad string. Real code guards both. We'll harden this when you actually ship the swap (Lesson 4) — for now, just see the shape of the seam.

This parseColor-in / toString-out pair is the single most transferable idea in the whole mission. Almost every “this library uses a richer type than my app does” problem is solved by exactly this seam.

Predict the output

Say it out loud, then reveal. Two subtle points hide here.

const c = parseColor("#f80");
const back = c.toString("hex");
// back === ?     c === ?  (unchanged?)
Reveal

back === "#FF8800" — note it expands and uppercases; "#f80" and "#FF8800" are the same color but not the same string. If your app does string equality on colors, round-tripping through a Color can change the string. And c is unchanged — Color is immutable; every operation returns a new one. That's why you always setColor(next) rather than mutating.
