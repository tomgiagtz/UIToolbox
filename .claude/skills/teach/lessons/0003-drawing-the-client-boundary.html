Drawing the client boundary

Last lesson gave you the map: prerender the shell, run in the browser. Since then the Glyph Creator tracer bullet landed — so here is that boundary drawn in your own code, and the one rule that keeps it safe.

The boundary is a doorway, not a label

"use client" does not mean "this file is browser code." It marks an entry point: from that line downward — through everything the file imports — the code ships to and runs in the browser. Above it, Server Components render at build and never reach the browser.¹

Your Glyph Creator crosses that doorway exactly once:

✓app/tools/glyph-creator/page.tsxServer Component — no directive, exports metadata. Renders at build; ships no JS. It draws the static chrome, then hands off…
◆glyph-creator.tsx · "use client"The boundary. Line 1. Below here is browser territory: useState, the file input, the Generate handler.
✓everything it importsPulled across into the client bundle — including glyph-preview.tsx, itself a second "use client" canvas component.

One page, one deliberate line. page.tsx stays a Server Component so the title, breadcrumb and intro prerender instantly (lesson 1); only the interactive tool costs client JavaScript.

Your three kinds of module

Open src/lib/glyph/ and every file sorts into one of these. Knowing which is the whole skill:

KindRuns whereNeeds "use client"?
Server Component
page.tsx · layout.tsx		 Build only No — it's the default
Client Component
glyph-creator · glyph-preview		 Build once, then browser Yes — this is the line
Pure logic
generate · packer · naming · slugify · presets · types		 Anywhere: build, browser, Vitest No — it's just TypeScript
Browser-only
font · renderer · compositor · exporter		 Browser only No, but must be called from a client component
Why the pure column matters generateTilesets and its helpers return DOM-free data — no window, no canvas. That is exactly why Vitest can test them with no browser (generate.test.ts, packer.test.ts) — the same green unit-test gate you decoded in the CI lesson. Pure logic is testable because it stayed off the browser.

Why it still prerenders (the subtle part)

Here is the trap most people miss: a Client Component is still prerendered once at build. So its first render must be DOM-free too — no canvas, no File, no document. Your tracer bullet gets this right, and it's worth seeing how:

✓loadFontFromFile(file)Uses FontFace + document.fonts — but is called inside onFontChange, an event handler. Never during render.
✓renderGlyph(ctx, …)Draws to <canvas> — but inside GlyphPreview's useEffect, behind a typeof document !== "undefined" guard. Fires only after hydration.
The one rule to keep Browser APIs go in event handlers or effects — never in the render body. At build there is no browser, so anything that touches window, canvas, or localStorage during render either crashes the prerender or makes the build's HTML disagree with the browser's — a hydration mismatch. (Your Date.now() in loadFontFromFile is safe precisely because it's in a handler, not render.)
