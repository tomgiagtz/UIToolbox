Ship the swap

Everything so far, turned into a real replacement in controls-ui.tsx — with the whole change confined to one file.

You have the model: state is a Color, subcomponents share it via context, you style its states with your tokens. Now the engineering question the mission is really about: where do you let this change ripple, and where do you stop it?

The decision that makes or breaks the swap

Your ColorField has three callers in style-controls.tsx (text color, background fill, border color), and each dispatches a reducer action whose payload is a string. The reducer and its tests speak strings. So the winning move is not to spread React Aria outward — it's to keep the exact same external API: 

// unchanged — the contract every caller and the reducer already rely on
{ label: string; value: string; onChange: (value: string) => void }
Contain the blast radius Rebuild ColorField internally on React Aria while its props stay identical. Then style-controls.tsx doesn't change, the reducer doesn't change, the tests don't change. The boundary seam lives inside the component — exactly where it belongs.

Two guards you can't skip

Crossing the string↔Color seam has two failure modes. Name them first:

1 parseColor(value) can throw If value is ever malformed (a loaded project, an empty string), parseColor throws and takes the render down. Wrap it in a safeParse with a fallback.
2 the casing round-trips onChange emits toString("hex") → uppercase ("#F8FAFC"). Same color, different string than the stored "#f8fafc". Harmless here (reducer just stores it), but know it happens.

(There's a would-be third — onChange giving Color | null — but that's for a bare ColorField that can be cleared. Wrapped in a ColorPicker that always holds a value, you get a non-null Color. A small reward for using the compound form.)

The replacement, annotated

This reuses the Lesson 2 compound pattern to rebuild your old look — a swatch beside a hex field — where ColorSwatch and the input both read the one color from the picker's context: 

"use client";

import {
  ColorPicker,
  ColorSwatch,
  ColorField as AriaColorField,
  Input,
  parseColor,
  type Color,
} from "react-aria-components";
import { cn } from "@/lib/utils";

/** Malformed strings must never crash the panel — fall back to black. */
function safeParse(value: string): Color {
  try {
    return parseColor(value);
  } catch {
    return parseColor("#000000");
  }
}

/** Same props as before — callers and the reducer are untouched. */
export function ColorField({
  label,
  value,
  onChange,
}: {
  label: string;
  value: string;
  onChange: (value: string) => void;
}) {
  return (
    <ColorPicker
      value={safeParse(value)}                        {/* string → Color, in  */}
      onChange={(c) => onChange(c.toString("hex"))}    {/* Color → string, out */}
    >
      <div className="flex flex-col gap-1.5">
        <span className="text-sm font-medium">{label}</span>
        <div className="flex items-center gap-2">
          <ColorSwatch className="h-9 w-12 rounded-md border border-input" />
          <AriaColorField aria-label={label} className="flex-1">
            <Input className={cn(inputClass, "w-full font-mono")} />
          </AriaColorField>
        </div>
      </div>
    </ColorPicker>
  );
}

Note two reuse wins: inputClass comes straight from the same file, and its existing focus-visible:ring-2 works because <Input> is a native input — no data-[focused]: rewrite needed here (Lesson 3's nuance, paying off). The seam — safeParse in, toString("hex") out — is those two lines and nothing more.

Watch — a real UX trade The old field was a native OS color well you clicked to open the system picker. This new one is a typeable hex field plus a read-only swatch — better for precise hex, but it drops the OS popover. If you want a visual picker back, that's a ColorArea + ColorSlider in a popover — more UI, same ColorPicker context. A deliberate choice, not an accident. Decide it on purpose.
