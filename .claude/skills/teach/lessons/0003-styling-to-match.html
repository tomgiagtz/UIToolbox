Styling it to match UIToolbox

React Aria ships almost no CSS on purpose. That's not a gap — it's the seam where your Tailwind goes in.

You've done questions 1, 2, and 4 of the reading method — state shape and how subcomponents share it. This is question 5: how is it styled? The surprising answer: it isn't, until you style it. react-aria-components give you behaviour, accessibility, and state, and leave every pixel to you. Your job is to attach your existing look — the same tokens in your inputClass — to their markup.

Two ways state reaches your CSS

A styled input needs to react to focus, hover, disabled, etc. React Aria hands you those states in two forms (docs). Same information, two shapes:

A data-* attributes Every state is a DOM attribute: data-focused, data-hovered, data-pressed, data-disabled, data-focus-visible. Style them like pseudo-classes — perfect for Tailwind.
B className / style as a function className can be a function of the state object: className={({isFocused}) => …}. Use when a class depends on JS logic, not just one flag.
The rule of thumb Reach for data-attributes first — they keep styling declarative and Tailwind-native. Drop to the function form only when the class depends on something a single attribute can't express (combining states, a computed value, a variant).

Data-attributes in your Tailwind

You're on Tailwind v4 with no React-Aria plugin, so use the built-in arbitrary variant syntax — data-[focused]:…. It targets the attribute directly; no plugin needed: 

<Input
  className="h-9 rounded-md border border-input bg-background px-3 text-sm
             data-[focused]:outline-none
             data-[focused]:ring-2 data-[focused]:ring-ring
             data-[disabled]:opacity-50 data-[disabled]:pointer-events-none" />

Look familiar? Those are the same tokens as your existing inputClass in controls-ui.tsx — border-input, bg-background, ring-ring. You are not inventing a new look; you're re-pointing your look at React Aria's states. The only real change: your old field used the CSS pseudo-class focus-visible:ring-2; here the equivalent state arrives as data-[focus-visible]:ring-2.

Watch — the naming gotcha React Aria's states are past-tense adjectives: data-hovered, data-focused, data-pressed — not the CSS :hover/:focus/:active you're used to. Write data-[hovered]:bg-accent, not hover:bg-accent, if you want React Aria's (more correct) notion of the state. (Plain hover: still works — it's just the browser's version, which ignores things like touch.)

The function form, when you need it

Sometimes one attribute isn't enough — you want a class only when focus-visible AND selected, or you're computing something. Then className as a function earns its keep (docs): 

<Radio className={({ isFocusVisible, isSelected }) => cn(
  "flex rounded-lg p-4 border",
  isSelected     && "bg-primary text-primary-foreground",
  isFocusVisible && "ring-2 ring-ring ring-offset-1",
)} />

Note cn(...) — your own helper from @/lib/utils (clsx + tailwind-merge). It belongs here for the same reason it's in button.tsx: it merges conditional classes and resolves Tailwind conflicts. The static-string and function forms can mix freely — plain string on the simple parts, function only where logic bites.

Putting it together — your field, restyled

Everything from Lessons 1–3 in one component: the boundary seam (state), one ColorField in a ColorPicker (subcomponents), and your tokens on React Aria's states (styling): 

import { ColorPicker, ColorField, Label, Input, parseColor } from "react-aria-components";
import { cn } from "@/lib/utils";

<ColorPicker
  value={parseColor(project.textColor)}                       {/* string → Color */}
  onChange={(c) => dispatch({ type: "set-text-color", color: c.toString("hex") })}
>
  <ColorField className="flex flex-col gap-1.5">
    <Label className="text-sm font-medium">Text color</Label>
    <Input className={cn(
      "h-9 rounded-md border border-input bg-background px-3 py-1 text-sm",
      "data-[focused]:outline-none data-[focused]:ring-2 data-[focused]:ring-ring data-[focused]:ring-offset-2",
      "data-[disabled]:opacity-50",
    )} />
  </ColorField>
</ColorPicker>

That's the whole replacement — recognisably UIToolbox, but now accessible, Color-object-backed, and ready to grow channels/sliders inside the same picker whenever you want them.

// You tab to the input. Does the ring appear via React Aria's state?
Reveal

The ring does appear — but through the browser's :focus-visible, not React Aria's state. Usually identical, so it looks fine. The subtle point: to bind to React Aria's own, more consistent notion (which it also sets on non-input elements that have no native focus pseudo-class), you'd write data-[focus-visible]:ring-2. On a plain <Input> either works; on composed elements (ColorSwatch, a custom trigger) only the data-attribute does.
