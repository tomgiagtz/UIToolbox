Rendering · Lesson 1 · Where & when

Where does my app render?

It felt weird to server-render an app that runs offline. That instinct is correct — and dissolving it turns "SSR" from a scary word into two plain questions you can answer for any route in UIToolbox.

Two questions hiding inside one word

"Render on the server" sounds like a single choice. It isn't. Every route answers two independent questions, and the confusion comes from collapsing them:

1. When is the HTML first built? — at build time, per request, or in the browser.
2. Where does the app run afterward? — on a live server, or in the browser.

Three named strategies are just three pairs of answers.¹ Full definitions live in the glossary — keep it open.

The one idea to keep Prerender renders on the server too — just at build time, not per request. That is the whole trick. "SSR" should mean only the per-request case; everything else people call "server rendering" for a static site is really prerender.

Your app, placed on the map

UIToolbox needs the highlighted column. Here is why, in your own terms:

✓next build (on your CI runner)The "server" that renders your HTML. It runs once, prerenders each route (/, /tools/glyph-creator), then goes away.
✓the browser receives HTMLInstant UI chrome — the heading, the "Coming soon" card — with no blank flash.
✓React hydratesThe static HTML becomes a live app in place. From here everything runs in the browser.
◆font upload · canvas glyphs · packing · exportAll local. No server sees the user's font — exactly what CONTEXT.md promises.

So you are not doing SSR. There is no per-request rendering anywhere. The only machine that "renders on a server" is your CI runner — the same npm run build gate you decoded in the CI lesson, running once.

A subtlety worth holding Today your next.config is empty, so npm run start serves those prerendered pages from a Node server. That still isn't SSR — nothing is rendered per request; the server just hands over files built earlier. Adding output: 'export' would drop even that server and emit a pure out/ folder.²

The boundary you're about to draw

Here is where this bites in practice. Your pages are Server Components by default,³ so they run during the build. But the glyph generator needs canvas, IndexedDB, an uploaded File — none of which exist at build time. Run that code during the prerender and it crashes.

The fix is a deliberate client boundary: put "use client" at the top of the interactive component. Everything below it ships to and runs in the browser — the right home for browser-only APIs. Placing that line on purpose, not by reflex, is the whole skill this thread is building toward.

Advantages & disadvantages (the part you asked about)

Why prerender at all, instead of pure CSR, if it's offline? Even with no server, prerendering buys an instant first paint (no blank screen while JS loads), a shell that shows with JS disabled, and clean SEO for the landing page. The cost: any browser-only code must be fenced below a client boundary, and mismatched HTML causes hydration errors.

Why not SSR? SSR's wins — per-request freshness, personalisation — are things UIToolbox never needs. Its costs — a server running at runtime, per-request latency, and no purely-static/offline deploy — are exactly what you're trying to avoid. For a tool that fetches nothing, SSR is all cost.
