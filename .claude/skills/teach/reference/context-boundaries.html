State & context boundaries

Where to draw the line between a library component's internal state and your app's state. Reusable for any library, not just React Aria.

The one rule

Pick one canonical owner For any single fact (e.g. “the text color”), exactly one layer owns the truth. Every other place that shows it is a derived view. Two owners = drift + sync bugs.

Canonical vs. working copy

The usual split when a library uses a richer type than your app:

LayerOwnsShapeLifetime
Your app state
(reducer / store)		 Canonical truth Whatever your app persists (e.g. hex string) Saved, undo/redo, survives unmount
Library context
(e.g. ColorPickerStateContext)		 Working copy while editing The library's rich type (e.g. Color) Ephemeral, lives in the subtree

The boundary adapter sits between them: parse on the way in, serialise on the way out (e.g. parseColor ↔ toString("hex")).

The knob: controlled vs. uncontrolled

Choosing this is choosing where the boundary sits.

Controlled — value + onChange

You own canonical state. Library context is a pure derived view. One source of truth = your store. Prefer this when other UI, persistence, or undo needs the value.

Uncontrolled — defaultValue

The library owns it in its context. You only hear changes via onChange. Fine for throwaway/local widgets nothing else reads.

How context actually costs you

  • Reads are free. A consumer walks up to the nearest provider — depth doesn't slow lookups. “Deep context” is never a read problem.
  • Re-renders are the cost. When a context value changes, every consumer re-renders, however far away. Cost = breadth × change-frequency, not depth.
  • Nesting = shadowing. The nearest provider of a given context wins for its subtree; outer ones are hidden. Each instance is isolated.
  • “Provider hell” (many stacked providers) is a readability smell, not a perf one. The perf smell is one wide context with a hot value.

Splitting your own contexts

  • By change frequency. Hot value (drag position, live color) in one context; stable config in another — so a fast update doesn't re-render config consumers.
  • Value vs. dispatch. Put dispatch in its own context; it's referentially stable, so dispatch-only consumers never re-render on value change.
  • By read audience. Don't hoist into a shared context something only one branch reads. Prefer local state or composition.
  • Prop-drilling 3+ levels → candidate for context — or just component composition (often the better fix).

The trap to avoid

Two-owner loop Never copy library state into your store with a useEffect while also feeding your store back down as value. That's two owners: they fight, they drift (your string says #f80; the Color says #FF8800), and you can get render loops. Pick one owner; the other side is always derived.

Decision flow

1Who else reads this fact?Only this widget → uncontrolled is fine. Anyone else (persistence, undo, other UI) → controlled.
2Where's the lowest common ancestor?Canonical state lives there — no higher. Lifting further than needed causes needless re-renders.
3Does the value change per frame/keystroke?If yes and it has many consumers, isolate it in its own narrow context.
✓Put the adapter at the seam.Parse in, serialise out. That line is the boundary between canonical and working copy.
